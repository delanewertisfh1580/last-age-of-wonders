# DEV-SPEC-TEMPLATE v1.0 — «Шаблон спецификации к разработке»

**Тип документа:** Шаблон (нормативный) для всех `DEV-SPEC-{NNN}`
**Дата:** 2026-11-04
**Статус:** утверждён как рабочий стандарт
**Основан на:** `DEV-SPEC-OVERVIEW v1.0` §1 (что обязана содержать спека), §2 (конвенции именования), §7 (Definition of Done); фактическая структура — согласованный профиль реализаций `DEV-SPEC-001…026`.
**Назначение:** единый каркас, по которому пишутся все новые спецификации к разработке, чтобы из них автоматически и без потерь выводились тикеты (`TICKETS-M{N}`).

---

## 0. Правила использования шаблона

1. **Нумерация секций обязательна и неизменна** (1–17). Секции, неприменимые к данной спеке, не удаляются — в них пишется одна строка: «Не применимо: {причина}» или «Вне scope → `DEV-SPEC-{NNN}`». Это позволяет CI и авторам тикетов парсить спеки по фиксированным заголовкам.
2. Каждая спецификация порождает **одну веху тикетов** `TICKETS-M{N}` (см. `TICKET-TEMPLATE v1.0`), где каждый тикет ссылается на конкретные `R`/`AC`/`§` этой спеки.
3. Все ID — по конвенциям OVERVIEW §2: `{SPEC-ID}-R{NN}`, `{SPEC-ID}-AC{NN}`, `{SPEC-ID}-T{NN}`. Нумерация сквозная, без пропусков; удалённое требование помечается `[DEPRECATED]`, номер не переиспользуется.
4. Язык документов — русский; идентификаторы, типы, события, пути файлов — английский, kebab-case для content-ID, PascalCase для типов.
5. `DESIGN`-документ — источник истины для решений. При противоречии приоритет у `DESIGN`, а противоречие фиксируется в §1.3 (колонка «Расхождения») и §15.
6. Статус-машина документа: `draft → review → approved → superseded(vX)`. Тикеты можно открывать только по `approved`; по `draft` — только research-тикеты с префиксом `RSC-`.
7. Балансовые числа в спеке запрещены (кроме значений контрактов протокола, например таймаутов доставки событий). Всё, что может крутиться балансиром, — data-driven поля + ссылка на будущий «Balance & Tuning» (OVERVIEW §8).

## 2. Зависимости

### 2.1. Обязательные
Список `DEV-SPEC-{NNN}` с указанием, какой именно контракт потребляется (например: «`DEV-SPEC-002` — `IEventBus`, `EventDefinition`»). Циклические зависимости недопустимы; мягкие стыки оформляются портом (§8), а не зависимостью.

### 2.2. Мягкие
Спеки, состояние которых читается через события/порты, но без которых спека собирается и тестируется (с заглушками).

### 2.3. Внешние
Библиотеки, рантайм (Bun/Node), браузерные API, инструменты (`ajv`, `vitest`) — с версиями и обоснованием.

## 4. Архитектурное размещение

### 4.1. Слои
Соответствие гексагональной схеме: какие классыdomain / infrastructure / application / bootstrap. Правило: domain не импортирует ничего кроме `core/primitives`; персистентность — только через tracker/memento.

### 4.2. Файлы
Полное дерево файлов, создаваемых спекой (реализационный контракт — пути и имена фиксированы):

```
src/domain/{context}/…
src/infrastructure/{context}/…
src/application/{context}/…
content/schemas/…
content/packs/{pack}/…
test/{context}/…
tools/ci/…
```

### 4.3. DI (GameContainer)
Таблица регистраций: токен → реализация → жизненный цикл (singleton/scoped) → стадия bootstrap, на которой регистрируется.

---

## 5. Domain-модель

Для каждой сущности — подсекция `5.N. {Имя}`: TypeScript-интерфейс целиком (со `Brand`-type'ами ID), инварианты с ID (`{CONTEXT}-INV-NN`), правила вывода/агрегации. Интерфейсы из спеки копируются в код без изменений; любое отклонение — открытый вопрос §15 до начала реализации.

---

## 6. Data-контракты и схемы

### 6.1. Механики (`MechanicDefinition`)
Таблица плагинов спеки: `id`, `scope`, `lifecycle`, `priority`, `state_schema` (ссылка), кто эмитит, кто персистит.

### 6.2. JSON Schema (`content/schemas/`)
Список схем с ключевыми ограничениями (`additionalProperties: false`, enum-ы, паттерны kebab-case ID, `if/then`-инварианты). Полные тела схем — в пакете `DEV-SPEC-003` либо вложенными блоками здесь.

### 6.3. Политики
`DeliveryPolicy`, ценовые/бойкие политики — ссылки на значения по умолчанию и место их переопределения контентом.

### 6.4. Событийный контракт
Новые события: `topic`, `payload_schema`, `delivery_policy`, `source` (`core` / `faction_extension`). Только регистрация в реестре `DEV-SPEC-002`; семантика — §7.

## 7. Рантайм-поведение

### 7.1. State machines
По одной на каждую машину состояний: ASCII/Mermaid-диаграмма + таблица переходов `(state, event, guard) → (state', effects)`; запрет недетерминированных переходов.

### 7.2. Sequence diagrams
Ключевые пользовательские/системные сценарии (нотация: участники → сообщения, с указанием Result-веток ошибок).

### 7.3. Tick-контракт
Фаза (`TickPhase`/scope), порядок относительно других доменов (§ из `DEV-SPEC-007`), бюджет такта, поведение при пропуске фазы.

### 7.4. Идемпотентность и детерминизм
Как RNG-потоки (`rng.{context}.{stream}`) выводятся из seed'а; правило «tick N даёт одинаковый результат при любом пути загрузки»; что входит в снимок.

### 7.5. Прочие алгоритмы
Нестандартные вычисления (жадные матчинги, графовые обходы) — псевдокод с инвариантами и сложностью.

---

## 8. Порты и адаптеры

### 8.1. Порты
TypeScript-интерфейсы портов целиком, каждая метода — сигнатура `(...): Promise<Result<T, AppError>>` или синхронный `Result`. Указать, кто владелец контракта (эта спека) и кто реализатор (другая спека).

### 8.2. Адаптеры
Реализации: `Null*Port` для тестов, production-адаптер, временные заглушки до выхода зависимой спеки.

### 8.3. Ошибки
Файл `{Context}Errors.ts`: коды `INFRA_*` / `DOMAIN_*` / `APP_*` с префиксом контекста, таблица «условие → код → recoverable?». Все ошибки — только через `Result<T, E>`; броски исключений запрещены (кроме bootstrap fail-fast).

---

## 9. Интеграционные точки

### 9.1. Потребляемые события
Таблица: `topic` → реакция → фаза.

### 9.2. Эмитируемые события
Таблица: `topic` → триггер → consumers (по спекам).

### 9.3. Мосты к другим доменам
Явные стыки (`CargoCapacityPort`, `EpilogueFactPort`, `cataclysm.* ↔ economy.*` и т.п.) — контракт здесь, реализация там.

### 9.4. Use cases (`application/{context}/`)
Список команд/запросов: имя → входной DTO → выходной DTO → используемые порты → публикуемые события.

---

## 10. Обработка ошибок
Сводная матрица: слой × тип отказа → код ошибки → действие системы (retry / degrade / fail fast) → сообщение локализации (ключ `errors.{context}.*`). Особо — что происходит при рассинхроне снимка, невалидном контенте, превышении бюджета такта.

---

## 11. Критерии приёмки

Для каждого требования `R{NN}` — подсекция `### {SPEC-ID}-R{NN} — {название}` с телом:

```
Требование: формальная формулировка (1–4 пункта).
Invariant: {CONTEXT}-INV-NN (если есть).

AC {SPEC-ID}-AC01 (Given/When/Then):
  Given …
  When  …
  Then  … (проверяемое утверждение с числом/кодом ошибки/событием)
```

Правила: минимум один AC на R; AC обязан быть машинно проверяемым (тест, CI-стадия, снапшот); в AC запрещены слова «быстро», «удобно», «корректно» без критерия.
