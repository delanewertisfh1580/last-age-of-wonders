# TICKET-TEMPLATE v1.0 — «Шаблон тикета разработки»

**Тип документа:** Шаблон (нормативный) для всех `TKT-M{N}-{NN}`
**Дата:** 2026-11-04
**Статус:** утверждён как рабочий стандарт
**Основан на:** `TICKETS-OVERVIEW v1.0` §2 (формат тикета), §3 (размеры), §8 (DoD вехи), §9 (правила работы); фактический профиль — `TICKETS-M1…M7`.
**Назначение:** правила вывода тикетов из готовой `DEV-SPEC-{NNN}` и единый формат блока тикета, пригодный для парсинга и трассировки.

---

## 1. Процесс: DEV-SPEC → веха тикетов

Вход: `DEV-SPEC-{NNN}` со статусом `approved` (все OQ, помеченные как блокеры, закрыты). Выход: файл `TICKETS-M{N} v1.0 — «{Название}».md` в `.workflow/ticket/Wave {W}/`.

Детерминированный алгоритм декомпозиции (порядок шагов фиксирован):

| Шаг | Источник в спеке | Тип тикета |
|---|---|---|
| 1 | §4.2 + §6.2 | **Registry/Schema**: маппинг `schemaNameForKind`, JSON-схемы, регистрация пакета в `content/packs.json` |
| 2 | §5 (по одной подсекции на сущность) | **Types+Content**: TS-типы (`Brand`-ID, инварианты) + минимальный контент-срез первой волны |
| 3 | §8.3 | **Errors**: `{Context}Errors.ts`, коды, подключение к Result-конвейеру |
| 4 | §8.1–8.2 | **Ports**: интерфейс порта + `Null*Port` заглушка |
| 5 | §7.5, §6.3 | **Pure resolvers**: детерминированные вычислители без состояния (политики, инвентарные операции) |
| 6 | §6.1 + §7.3 | **Mechanic plugins**: по одному тикету на механику (tracker/resolver) |
| 7 | §7.4 + §6.x снимки | **Memento provider**: снимок/восстановление + валидация |
| 8 | §6.4 + §9.1–9.2 | **Events**: регистрация событийного ядра контекста |
| 9 | §9.4 | **Use cases**: команды/запросы прикладного слоя (каждый use case — S/M тикет) |
| 10 | §12.6 | **CI**: расширение стадий graph/lint/determinism под контекст |
| 11 | §4.3 + §12.5 | **Bootstrap+Demo**: DI-регистрации, сборка, `demo:m{N}` E2E-сценарий |

Правила декомпозиции:
- Каждый тикет ссылается минимум на одно `R` и максимум на 3 смежные `R`; каждый AC входит ровно в один «головной» тикет (в DoD остальных он допускается как проверка).
- Тикет размером `L` запрещён — делить до `M` (легенда §3 OVERVIEW).
- Порядок зависимостей строится по таблице выше (шаги n могут зависеть только от ≤ n); внутри шага — параллельно.
- Запрещено создавать тикеты, не имеющие ссылки на секцию спеки (`**DEV-SPEC:** …§…`).


## 3. Формат блока тикета (обязательные поля)

````
### TKT-M{N}-{NN} — {Императивное название: что делается}

**DEV-SPEC:** DEV-SPEC-{NNN} §{x.y}[, §{x.z}]
**Требования:** R{NN}, R{NN}
**AC:** AC{NN}, AC{NN}
**Размер:** XS / S / M
**Зависит от:** TKT-… | Wave {W} (M{x}) | —
**Блокирует:** TKT-… | DEV-SPEC-{MMM}

**Что сделать:**
- конкретные правки с путями файлов и именами типов/функций;
- каждое действие проверяемо («добавить X», а не «реализовать поддержку X»);
- перечень тестов, которые должны появиться (по ID из §12 спеки).

**Acceptance Criteria:**
- `DEV-SPEC-{NNN}-AC{NN}`: машинно проверяемое утверждение (вывод теста / код ошибки / факт события).

**Definition of Done:**
- [ ] scope выполнен полностью, без «времённок»;
- [ ] все заявленные AC покрыты тестами;
- [ ] `t:type` зелёный;
- [ ] `t:test` зелёный;
- [ ] `ci:validate` зелёный (или соответствующая стадия);
- [ ] PR смержен, трассировка R→AC→T→TKT обновлена.
````

Пояснения к полям:
- **Название** — глагол + объект («PricePolicyResolver», «Механика economy-trade-agents-sim»), без «реализация/доработка/поддержка».
- **Размер**: `XS` <2 ч (типы, хелперы), `S` 0.5–1 день (реализация с тестами), `M` 1–2 дня (use case, CI-стадия, state validator). Оценка ставится на момент создания; переоценка — комментарием, не изменением числа.
- **Зависит от/Блокирует** — только ID тикетов или ID спек; никаких текстовых «после интеграции».
- Пустое поле недопустимо: если зависимостей нет — `—`.

## 4. Соглашения об ID

| Артефакт | Формат |
|---|---|
| Тикет | `TKT-M{N}-{NN}` (NN сквозной в вехе, 01…) |
| Research-тикет | `RSC-M{N}-{NN}` (не создаёт кода, закрывает OQ) |
| Ссылка на требование | `[DEV-SPEC-{NNN}-R{NN}]` |
| Ссылка на критерий | `DEV-SPEC-{NNN}-AC{NN}` |
| Ссылка на тест | `DEV-SPEC-{NNN}-T{NN}` |

## 5. Чек-лист качества вехи перед открытием работ
(расширение OVERVIEW §8)

- [ ] каждая `R` спеки покрыта хотя бы одним тикетом; каждый `AC` — ровно одним головным тикетом;
- [ ] граф §2 ацикличен, есть единственный «вход» (шаг 1) и «выход» (bootstrap+demo);
- [ ] ни один тикет не зависит от незакрытого OQ (§15 спеки);
- [ ] демо-тикет (`demo:m{N}`) ссылается на §12.5 спеки и завершает веху;
- [ ] суммарная оценка вехи ≤ {ёмкость спринта}; иначе — перенос хвоста в следующую веху списком;
- [ ] файл вехи добавлен в «Mapping DEV-SPEC → Milestone → тикеты» соответствующего TICKETS-OVERVIEW.

## 6. Правила жизненного цикла тикета
- Статусы: `todo → in-progress → review → done` (+ `blocked-by: OQ/TKT`).
- Изменение scope тикета после открытия — только через новый тикет, не редактированием старого.
- При смене решения в DESIGN/DEV-SPEC затронутые `done`-тики не трогаются; создаётся корректирующий тикет со ссылкой на новую версию спеки.
