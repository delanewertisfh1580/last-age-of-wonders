## 1. Назначение и границы спецификации

Настоящая спецификация нормативно описывает менеджмент отряда как data-driven доменную подсистему, охватывающую структуру отряда, модель найма и развития напарников, экипировку, мораль, нарративные реакции и интеграцию со всеми аспектами мира.

**Спецификация фиксирует:**
- границы доменного контекста `Party`;
- модель отряда как набора напарников (без рядовых бойцов);
- жёсткое разделение корабельного экипажа и боевого отряда;
- модель найма напарников через нарратив/квесты/репутацию;
- бесклассовую систему прокачки через использование (Battle Brothers);
- полную экипировку по слотам с стыком с экономикой;
- гибридную модель морали (глобальная + настроения + шрамы);
- контракт `CompanionDefinition` с механиками, отношениями и нарративом;
- фиксированное содержание и зарплату по контракту;
- полный нарративный слой с личными арками;
- plugin-based архитектуру на базе полного переиспользования `MechanicDefinition`;
- событийную модель и мосты с другими доменами;
- модель RNG, сохранений и требования к CI.

**Спецификация не фиксирует:**
- числовой баланс (статы, урон, HP, тайминги, шансы);
- финальные тексты, лорные названия, арт, VFX, аудио;
- мобильный UX и конкретные экраны;
- детали генератора эпилога и миграции сохранений;
- детали скрытых веток трансформации (только хуки и контракты);
- детали боя, дуэли, экономики, катаклизмов (только контрактные мосты);
- конкретные нарративные тексты.

Это сознательный выбор уровня нормативно-контрактной детализации: документ должен позволять декомпозировать работу в тикеты, не замораживая баланс и контент prematurely.

## 2. Ключевые нормативные решения

### SPEC-PARTY-001. Границы доменного контекста `Party`

`Party` владеет **только боевым отрядом**, состоящим из напарников. Капитан, корабль, корабельный экипаж, инвентарь трюма находятся в других контекстах (`Captain`, `Fleet`, `Economy`).

**Правила:**
- `Party` не владеет состоянием капитана;
- `Party` не владеет состоянием корабля;
- `Party` не владеет корабельным экипажем;
- `Party` общается с другими контекстами только через события и порты.

### SPEC-PARTY-002. Отряд состоит только из напарников

Боевой отряд состоит **исключительно из напарников**. Рядовые бойцы отсутствуют как класс сущностей.

**Правила:**
- каждый член отряда — это `Companion`;
- напарники могут быть как лидерами подотрядов, так и одиночками-специалистами;
- нет разделения на "лидеров" и "рядовых" внутри отряда;
- размер отряда ограничен слотами напарников (data-driven).

### SPEC-PARTY-003. Жёсткое разделение экипажа и отряда

Корабельный экипаж (из SPEC-FLEET) и боевой отряд (напарники) — **жёстко разделённые сущности**.

**Правила:**
- корабельный экипаж обслуживает корабль (орудия, парус, ремонт);
- боевой отряд (напарники) абордирует и дерётся в дуэли;
- пересечение только через лимит "всего людей на борту";
- напарники не обслуживают корабль в бою;
- экипаж не участвует в абордаже.

### SPEC-PARTY-004. Структура отряда

Отряд имеет структуру: **капитан + пул напарников**.

**Правила:**
- капитан — отдельная сущность (стык с будущей спекой капитана);
- напарники — пул `Companion` с уникальными механиками;
- напарники могут командовать подотрядами в бою (стык с SPEC-COMBAT);
- напарники могут быть одиночками-специалистами;
- структура декларируется через `party_structure_policy_id`.

### SPEC-PARTY-005. Модель найма напарников

Напарники набираются **только через нарратив/квесты/репутацию**. Наём на рынке труда отсутствует.

**Правила:**
- напарники открываются через квесты, события, репутацию;
- каждый напарник имеет `acquisition_policy_id`;
- пленные могут быть конвертированы в напарников через `conversion_policy_id` с риском;
- нет случайного найма на рынке;
- конкретные условия — data-driven.

### SPEC-PARTY-006. Бесклассовая система прокачки

Напарники развиваются через **использование навыков** (Battle Brothers модель). Классы отсутствуют.

**Правила:**
- нет жёстких классов или архетипов;
- навыки развиваются через использование;
- перки выбираются из доступного пула;
- прокачка декларируется через `progression_policy_id`;
- конкретные числа — вне scope.

### SPEC-PARTY-007. Полная экипировка по слотам

Каждый напарник имеет **полную экипировку по слотам**: оружие, броня, шлем, аксессуар, расходники.

**Правила:**
- каждый слот — отдельный `EquipmentDefinition`;
- экипировка стыкуется с экономикой через товары;
- экипировка влияет на статы и механики;
- экипировка декларируется через `equipment_policy_id`;
- конкретные числа — вне scope.

### SPEC-PARTY-008. Гибридная модель морали

Мораль отряда — **гибридная**: глобальная мораль + индивидуальные настроения + перманентные шрамы.

**Правила:**
- глобальная мораль отряда — агрегированный счётчик;
- индивидуальные настроения — короткоживущие эффекты;
- перманентные шрамы — последствия ключевых событий (потеря друга, предательство);
- шрамы стыкуются с катаклизмами (SPEC-CATA);
- все компоненты декларируются через политики.

### SPEC-PARTY-009. Контракт напарника

Напарник = `CompanionDefinition` + набор механик (2–3) + дерево отношений с капитаном + личный нарратив.

**Правила:**
- напарник имеет уникальные механики через `MechanicDefinition`;
- напарник имеет дерево отношений с капитаном;
- напарник имеет личный нарратив (арка, реакции);
- напарник публикует факты в `EpilogueFactPort`;
- контракт един для всех напарников.

### SPEC-PARTY-010. Содержание и зарплата

Напарники получают **фиксированное содержание за такт** + зарплату по контракту.

**Правила:**
- содержание декларируется через `maintenance_policy_id`;
- зарплата декларируется через `salary_policy_id`;
- просрочка → падение морали → дезертирство;
- конкретные числа — вне scope.

### SPEC-PARTY-011. Полный нарративный слой

Напарники имеют **полный нарративный слой**: личные арки, реакции на все мировые события, влияние на скрытые ветки.

**Правила:**
- личные арки декларируются через `personal_arc_policy_id`;
- реакции на события декларируются через `reaction_policy_id`;
- влияние на скрытые ветки через давление/репутацию/клятвы;
- все реакции — data-driven;
- публикация фактов в `EpilogueFactPort`.

### SPEC-PARTY-012. Переиспользование механик

Полное переиспользование `MechanicDefinition` из SPEC-FLEET.

**Правила:**
- механики напарников живут в общем реестре;
- namespace событий — `party.*`;
- механики используют те же правила валидации;
- `role_tags` обязательно содержит `companion`;
- контракт `MechanicDefinition` един для всех доменов.

### SPEC-PARTY-013. Событийная модель

Ядро + фракционные расширения (аналогично SPEC-FLEET-042 и SPEC-ECON-082).

**Правила:**
- каноническое ядро обязательно для ContentRegistry;
- фракционные расширения — в пространстве имён фракций;
- мосты с другими доменами — через порты.

### SPEC-PARTY-014. Модель RNG

Именованные изолированные потоки: `rng.party.morale`, `rng.party.progression`, `rng.party.reactions`, `rng.party.recruitment`.

**Правила:**
- каждый поток изолирован;
- каждый поток именован;
- смешение потоков запрещено;
- вся случайность — через seeded RNG service.

### SPEC-PARTY-015. Модель сохранений

Полные JSON-снимки состояния отряда + журнал ключевых событий для нарратива и генератора эпилога.

**Правила:**
- состояние отряда сохраняется через полные снимки (Memento pattern);
- отдельный массив `party_events_journal` хранит ключевые события;
- снимки валидируются по JSON Schema.

### SPEC-PARTY-016. Уровень валидации и CI

Schema + graph + gameplay lint (аналогично SPEC-FLEET-083).

**Правила:**
- schema validation — обязательна;
- graph integrity — обязательна;
- gameplay lint — обязателен.

### SPEC-PARTY-017. Масштаб первой волны

Полный срез: 3–5 напарников с уникальными механиками + экипировка + мораль + шрамы + нарративные реакции + хуки скрытых веток + мосты с боем, экономикой, катаклизмами, нарративом.

## 3. Data-контракты

### SPEC-PARTY-020. Общие правила JSON-контента

`snake_case` для полей, `kebab-case` для ID. Все display-имена выносятся в локализацию.

**Примеры ключей локализации:**
- `companion.captain-ally.name`
- `companion.steam-engineer.description`
- `equipment.iron-sword.name`
- `party.morale.high`

### SPEC-PARTY-021. `CompanionDefinition`

**Пример структуры:**
```json
{
  "id": "companion-steam-engineer",
  "display_name_key": "companion.steam-engineer.name",
  "description_key": "companion.steam-engineer.description",
  "base_stats": {
    "hp": 120,
    "strength": 12,
    "agility": 8,
    "endurance": 14
  },
  "mechanic_ids": [
    "companion-steam-pressure-boost-resolver",
    "companion-steam-repair-tracker"
  ],
  "relationship_tree_policy_id": "steam-engineer-relationship",
  "personal_arc_policy_id": "steam-engineer-arc",
  "acquisition_policy_id": "steam-engineer-quest",
  "progression_policy_id": "skill-based-progression",
  "equipment_policy_id": "engineer-equipment",
  "maintenance_policy_id": "standard-maintenance",
  "salary_policy_id": "engineer-salary",
  "reaction_policy_id": "engineer-reactions",
  "vulnerability_tags": ["pressure", "fire"],
  "counterplay_tags": ["cold", "machine"]
}
```

**Правила:**
- `id` уникален;
- `base_stats` не хранит числовой баланс;
- `mechanic_ids` — ссылки на `MechanicDefinition`;
- все политики — data-driven;
- напарник не хранит рантайм-состояние.

### SPEC-PARTY-022. `EquipmentDefinition`

**Пример:**
```json
{
  "id": "equipment-iron-sword",
  "display_name_key": "equipment.iron-sword.name",
  "slot": "weapon",
  "stat_modifiers": {
    "strength": 5,
    "agility": 2
  },
  "tags": ["melee", "cutting"],
  "good_id": "iron-sword",
  "durability_policy_id": "iron-durability"
}
```

**Правила:**
- `slot` — один из нормативных слотов;
- `stat_modifiers` не хранит числовой баланс;
- `good_id` — ссылка на товар из SPEC-ECON;
- экипировка декларируется в данных.

### SPEC-PARTY-023. Переиспользование `MechanicDefinition`

Механики напарников используют тот же контракт, что и корабельные, с обязательными `role_tags` (например, `["companion", "combat"]`) и строгим разделением на resolver и tracker.

**Пример резолвера:**
```json
{
  "id": "companion-steam-pressure-boost-resolver",
  "kind": "resolver",
  "faction_tags": ["industrial-steam"],
  "branch_tags": [],
  "ship_class_tags": [],
  "facet_tags": [],
  "role_tags": ["companion", "combat"],
  "params": {},
  "consumes": [
    "combat.duel_action_executed",
    "party.companion_action_executed"
  ],
  "emits": [
    "party.companion_pressure_boosted"
  ],
  "state_schema": null,
  "counterplay_tags": ["pressure", "fire"],
  "validation_rules": {
    "params_schema": { "type": "object" }
  },
  "priority": 100,
  "lifecycle": {
    "scope": "companion",
    "persisted": false
  }
}
```

**Пример трекера:**
```json
{
  "id": "companion-steam-repair-tracker",
  "kind": "tracker",
  "faction_tags": ["industrial-steam"],
  "branch_tags": [],
  "ship_class_tags": [],
  "facet_tags": [],
  "role_tags": ["companion", "support"],
  "params": {},
  "consumes": [
    "world.tick_advanced",
    "party.companion_action_executed"
  ],
  "emits": [
    "party.companion_repair_ready"
  ],
  "state_schema": {
    "$id": "mechanics/companion-steam-repair-tracker/1",
    "type": "object",
    "properties": {
      "repair_charges": { "type": "number" },
      "last_used_tick": { "type": "number" }
    },
    "required": ["repair_charges"]
  },
  "counterplay_tags": ["sabotage"],
  "validation_rules": {
    "params_schema": { "type": "object" }
  },
  "priority": 90,
  "lifecycle": {
    "scope": "companion",
    "persisted": true
  }
}
```

**Правила:**
- контракт `MechanicDefinition` един для всех доменов;
- `role_tags` обязательно содержит `companion`;
- namespace событий — `party.*`;
- механики проходят те же проверки валидации.

## 4. Событийная модель

### SPEC-PARTY-030. Каноническое ядро

**Нормативный минимум:**

| Событие | Назначение |
|---------|------------|
| party.companion_recruited | напарник нанят |
| party.companion_dismissed | напарник уволен |
| party.companion_died | напарник погиб |
| party.companion_wounded | напарник ранен |
| party.companion_traumatized | напарник получил травму |
| party.companion_equipment_changed | экипировка изменена |
| party.companion_skill_improved | навык улучшен |
| party.companion_relationship_changed | отношение с капитаном изменилось |
| party.companion_mood_changed | настроение изменилось |
| party.companion_scar_applied | шрам наложен |
| party.companion_scar_removed | шрам снят |
| party.morale_changed | мораль отряда изменилась |
| party.salary_paid | зарплата выплачена |
| party.salary_overdue | зарплата просрочена |
| party.reaction_triggered | реакция напарника сработала |
| party.personal_arc_advanced | личная арка продвинулась |

**Правила:**
- эти события обязательны для ContentRegistry;
- механики напарников могут ссылаться только на зарегистрированные события;
- фракции не могут переопределять семантику ядерных событий.

### SPEC-PARTY-031. Фракционные расширения

Каждая фракция объявляет события в своём пространстве имён:
- `party.industrial-steam.*`
- `party.ancient-arcane.*`
- `party.necromantic-corpse.*`
- `party.living-artifact.*`

**Примеры:**
- `party.industrial-steam.engineer-boost-activated`
- `party.ancient-arcane.mage-ritual-performed`
- `party.necromantic-corpse.necromancer-ritual-performed`
- `party.living-artifact.artifact-adaptation-triggered`

**Правила:**
- фракционное событие обязано быть зарегистрировано;
- обязано иметь payload schema;
- не может совпадать по ID с ядерным событием;
- не может ломать ядерную семантику.

### SPEC-PARTY-032. Мосты с другими доменами

**Мост party ↔ fleet:**
- `fleet.ship_acquired` → `party.ship_changed`
- `fleet.ship_lost` → `party.ship_changed`

**Мост party ↔ economy:**
- `party.salary_paid` → `economy.expense_recorded`
- `party.companion_equipment_changed` → `economy.item_acquired`

**Мост party ↔ cataclysms:**
- `cataclysm.effect_applied` → `party.companion_reaction_triggered`
- `party.companion_scar_applied` → `cataclysm.scar_recorded`

**Мост party ↔ combat:**
- `combat.started` → `party.combat_started`
- `combat.ended` → `party.combat_ended`
- `party.companion_died` → `combat.crew_died`

**Мост party ↔ narrative:**

Публикация фактов в `EpilogueFactPort`:
- `epilogue.party.recruited_companion`
- `epilogue.party.lost_companion`
- `epilogue.party.companion_betrayed`
- `epilogue.party.companion_saved_captain`
- `epilogue.party.became_guild_master`

**Правила:**
- мосты декларативны;
- каждый мост имеет нормативный набор событий;
- мосты не раскрывают внутреннюю логику смежных доменов.

## 5. Детерминизм и RNG

### SPEC-PARTY-040. Детерминизм

Симуляция отряда полностью детерминирована от seed.

**Правила:**
- обязательна для тестов и реплеев;
- вся случайность — через seeded RNG service;
- сохранение + загрузка дают идентичное продолжение.

### SPEC-PARTY-041. Именованные потоки RNG

**Нормативные потоки:**

| Поток | Назначение |
|-------|------------|
| rng.party.morale | изменения морали |
| rng.party.progression | прокачка навыков |
| rng.party.reactions | реакции напарников |
| rng.party.recruitment | найм напарников |

**Правила:**
- каждый поток изолирован;
- каждый поток именован;
- смешение потоков запрещено.

## 6. Сохранения и состояние

### SPEC-PARTY-050. Полные JSON-снимки + журнал

Состояние отряда сохраняется через полные снимки `PartyInstance` (Memento pattern).

Отдельный массив `party_events_journal` хранит ключевые события для использования генератором эпилога.

**Правила:**
- каждый отряд имеет снимок;
- снимок валидируется по JSON Schema;
- журнал событий — отдельный массив;
- загрузка не восстанавливает поведение через журнал дельт;
- Memento pattern из GD-09 остаётся основным механизмом.

### SPEC-PARTY-051. Валидация при загрузке

При загрузке:
- состояние отряда проверяется по JSON Schema;
- состояние напарников проверяется по JSON Schema;
- состояние трекеров проверяется по JSON Schema;
- несоответствие схемы считается повреждением сохранения;
- миграции схем выносятся в отдельную будущую задачу.

## 7. Валидация и CI

### SPEC-PARTY-060. Уровень валидации

Обязательный уровень: Schema + graph + gameplay lint.

### SPEC-PARTY-061. Schema validation

**Проверяются:**
- соответствие JSON Schema;
- обязательные поля;
- типы полей;
- enum-ы;
- уникальность ID;
- корректность `kind` механик;
- наличие `state_schema` у трекеров;
- отсутствие persisted state у резолверов;
- корректность ссылок на события;
- корректность ссылок на механики;
- корректность ссылок на напарников, экипировку.

### SPEC-PARTY-062. Graph integrity

**Проверяется целостность графа контента:**
```
PartyInstance
  → CompanionDefinition[]
    → MechanicDefinition[]
      → EventDefinition[]
    → EquipmentDefinition[]
```

**Обязательные проверки:**
- каждый напарник имеет базовые статы;
- каждый напарник имеет минимум 2 механики;
- каждая экипировка имеет слот;
- все referenced mechanics существуют;
- все referenced events существуют;
- все referenced equipment существует.

### SPEC-PARTY-063. Gameplay lint

**Дополнительные игровые проверки:**
- каждый напарник имеет минимум 1 контрплейный тег;
- отсутствие циклических ссылок;
- все `mechanic_ids` существуют в реестре и имеют корректные `role_tags` с `companion`;
- каждый напарник имеет минимум одну реакцию на ключевые события;
- каждый напарник имеет личную арку;
- ContentRegistry не должен содержать дублирующихся ID.
