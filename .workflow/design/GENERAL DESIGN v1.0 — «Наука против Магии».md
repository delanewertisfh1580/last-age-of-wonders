## 1. Назначение документа

Этот документ переводит утверждённые намерения (Intent v1.0) в высокоуровневую архитектуру, определяет границы подсистем, потоки данных и решает ключевые технические противоречия.

## 2. Технологический стек (GD-01)

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| **Язык** | TypeScript (строгая типизация) | Поддержка DDD, data-driven, тестируемость |
| **Сборщик** | Vite | Быстрая разработка, HMR, оптимизация |
| **Рендер-движок** | **Babylon.js** | Полноценный 3D WebGL-движок с поддержкой стилизованных шейдеров, мобильной оптимизации, встроенной GUI-системы |
| **3D-графика** | WebGL + кастомные шейдеры | Стилизованный 3D (не фотореализм) |
| **Хранилище** | LocalStorage | Офлайн-сохранения без сервера |
| **DI-контейнер** | tsyringe или inversify | Лёгкий DI с декораторами |

**GD-01.1. Отказ от Phaser:** Phaser заменён на Babylon.js из-за ограничений Phaser в 3D-графике и необходимости полноценной поддержки стилизованных 3D-шейдеров с мобильной оптимизацией.

## 4. Механизм коммуникации между слоями (GD-04)

**GD-04. Domain Events:** основной механизм коммуникации — событийно-ориентированная архитектура через `IEventBus`.

### 4.1. Поток данных
1 Пользователь → UI → Сцена → Use Case
2 Use Case → Домен (изменение состояния)
3 Домен → Domain Events (через IEventBus)
4 Domain Events → Инфраструктура (рендер, аудио, хранилище)
5 Domain Events → Презентация (обновление UI)

### 4.2. Примеры событий

- `CompanionDied` → рендер удаляет напарника из сцены, UI обновляет список отряда, аудио играет траурную тему
- `CataclysmTriggered` → рендер добавляет визуальные эффекты, UI показывает предупреждение, аудио переключается на тревожную тему
- `TradeCompleted` → UI обновляет инвентарь и баланс, рендер показывает анимацию передачи товаров

## 5. Игровой цикл и тактовая модель (GD-05, GD-06)

**GD-05. Гибридная модель игрового цикла:**

- **Фоновая симуляция мира** (экономика, геополитика, катаклизмы, старение) — работает по тактам (например, 1 игровой день = 1 реальная секунда).
- **Активная симуляция** (бои, дуэли, торговля, диалоги) — запускается по действиям игрока или событиям мира.
- **Рендер Babylon.js** работает отдельно от доменной симуляции и интерполирует состояние для плавности (60 FPS).

**GD-05.1. Единая событийная модель:** события игрока и события фоновой симуляции поступают в активную симуляцию через общий механизм доменных событий и имеют равные права на влияние на состояние игры.

**GD-06. Политика доставки событий:** каждое доменное событие имеет политику доставки (`DeliveryPolicy`):

| Политика | Описание | Пример |
|----------|----------|--------|
| `Immediate` | Немедленное вмешательство | Смерть напарника, критическое ранение капитана |
| `NextTick` | Применение на следующем такте | Изменение погоды |
| `AfterScene` | Применение после завершения текущей сцены | Падение города, смена правителя |
| `WarningThenImpact` | Сначала предупреждение, затем воздействие | Надвигающийся катаклизм |

Каждая активная сцена определяет, какие политики она поддерживает.

## 6. Data-driven архитектура (GD-07, GD-08)

**GD-07. Data-driven дисциплина:** домен работает только с абстракциями и контрактами. Конкретные фракции, корабли, напарники, товары, квесты, катаклизмы — это данные (JSON), загружаемые через `ContentRegistry`. Добавление нового контента не требует изменения доменной логики.

### 6.1. Модель контента

1. **Content Definitions** — статические JSON-файлы, описывающие "что это":
   - `FactionDefinition` — фракция
   - `ShipDefinition` — тип корабля
   - `CompanionDefinition` — напарник
   - `TradeGoodDefinition` — товар
   - `QuestDefinition` — квест
   - `CataclysmDefinition` — катаклизм

2. **Content Registry** — инфраструктурный сервис, который:
   - Загружает JSON-файлы при старте
   - Валидирует их по схемам (TypeScript-интерфейсы)
   - Предоставляет домену доступ по ID (`getShipDefinition(id)`)

3. **Runtime Instances** — доменные сущности, создаваемые на основе определений:
   - `Ship` (экземпляр) = `ShipDefinition` + текущее состояние
   - `Companion` (экземпляр) = `CompanionDefinition` + текущее состояние

**GD-08. Детальные схемы дефинишенов** (поля, валидация, баланс между сложностью и количеством) — выносятся в **отдельный набор задач на этапе Specifications**.

## 7. Сохранения и состояние игры (GD-09, GD-10)

**GD-09. Memento pattern:** домен предоставляет метод `getState()`, возвращающий снимок всего состояния. Инфраструктура сериализует в JSON и сохраняет в LocalStorage. Загрузка = десериализация + восстановление доменного состояния.

**GD-10. Автосохранения:** отсутствуют по умолчанию. Автосейвы включаются только если игрок явно выбрал этот режим в настройках. Сохранения — только ручные или по явному запросу.

---

## 8. Сцены и управление рендером (GD-11, GD-12, GD-13)

**GD-11. Отдельные сцены для каждого режима:** каждая игровая активность — отдельная Babylon.js сцена (`WorldMapScene`, `CombatScene`, `CityScene`, `DuelScene`). `SceneManager` координирует переходы: выгружает одну сцену, загружает другую.

**GD-12. Сцены не знают о домене напрямую.** Сцены подписываются на доменные события через `IEventBus` и реагируют на них. Сцены отправляют команды в домен через Use Cases из прикладного слоя.

**GD-13. Прямые вызовы Use Cases:** сцены получают ссылки на Use Cases и вызывают их напрямую (без Command Bus). Это обеспечивает слабую связанность без избыточности.

## 9. Мобильная адаптация (GD-14)

**GD-14. Адаптивный UI через CSS + Babylon.js GUI:**

- **Основной UI** (меню, HUD, диалоги, инвентарь) — HTML/CSS с адаптивной версткой (media queries, flexbox/grid, относительные единицы).
- **Babylon.js GUI** — только для внутриигровых элементов, тесно связанных с 3D-сценой (индикаторы здоровья корабля, мини-карта, маркеры целей).
- **Система ввода** (`presentation/input/`) определяет устройство и переключает обработчики (`DesktopInputHandler` / `MobileInputHandler`).
- **Сцены** проектируются с учётом производительности на мобильных устройствах (упрощённые шейдеры, LOD, ограничение количества объектов).

## 10. Нарративная аудио-система (GD-15)

**GD-15. Децентрализованные аудио-адаптеры по сценам:**

- Каждая сцена имеет свой аудио-адаптер (`SceneAudioAdapter`).
- Адаптер подписывается на доменные события и анализирует текущее состояние мира для выбора музыкальной темы и звуковых эффектов.
- Глобальный `AudioManager` координирует переходы между сценами и управляет глобальными настройками.
- Музыкальные темы и условия воспроизведения — данные (JSON), загружаемые через `ContentRegistry`.
- Адаптеры сцен могут наследовать общую логику через базовый класс или композицию.

## 11. Dependency Injection (GD-16)

**GD-16. Лёгкий DI-контейнер:** используем `tsyringe` или `inversify` с декораторами (`@injectable`, `@inject`) для автоматической инъекции зависимостей. В `bootstrap/` регистрируем все зависимости и запускаем композицию.

---

## 12. Обработка ошибок (GD-17)

**GD-17. Result pattern:** Use Cases и доменные сервисы возвращают `Result<T, E>` вместо бросания исключений. `Result` содержит либо успешное значение (`T`), либо ошибку (`E`). Прикладной слой явно обрабатывает ошибки и преобразует их в пользовательские сообщения.

## 13. Ключевые потоки данных

### 13.1. Торговля в городе
1 Игрок входит в город → SceneManager загружает CityScene
2 CityScene подписывается на доменные события
3 Игрок открывает торговый диалог → UI вызывает Use Case GetTradeOffers
4 Use Case запрашивает у домена доступные товары и цены
5 Домен возвращает DTO с предложениями
6 UI отображает товары
7 Игрок выбирает товар и количество → UI вызывает Use Case ExecuteTrade
8 Use Case проверяет условия (деньги, место в трюме) через домен
9 Домен меняет состояние (убирает товары из города, добавляет в трюм, меняет баланс)
10 Домен генерирует событие TradeCompleted
11 CityScene получает событие → обновляет визуал (анимация передачи товаров)
12 UI получает событие → обновляет инвентарь и баланс
13 AudioAdapter получает событие → играет звук успешной сделки


### 13.2. Морской бой с фоновым событием
1 Игрок встречает вражеский корабль → SceneManager загружает CombatScene
2 CombatScene подписывается на доменные события
3 Игрок выбирает манёвр → UI вызывает Use Case ExecuteManeuver
4 Домен обновляет позиции кораблей, генерирует события ManeuverExecuted
5 CombatScene получает событие → анимирует движение кораблей
6 В это время фоновая симуляция генерирует событие CataclysmStormApproaching (политика WarningThenImpact)
7 CombatScene получает предупреждение → показывает визуальный эффект приближающегося шторма
8 Через несколько тактов фоновая симуляция генерирует CataclysmStormEntered (политика Immediate)
9 CombatScene получает событие → меняет условия боя (ветер, видимость)
10 Домен обновляет параметры боя (скорость кораблей, точность орудий)
11 Бой продолжается с новыми условиями
